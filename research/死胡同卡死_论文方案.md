## 1. 先把卡点钉死（不是猜的）

### 1.1 时间线

88 s 内从 `(-4.70,-4.04)` 沿 12° 坡爬到 `(-4.91,2.70)`（地面高度估计 0.328 m，坡度识别正确），**随后约 30 s 零位移**，以 `stalled` 结束，终点误差 1.634 m，碰撞 0。

和你看到的视频一致：蓝色轨迹是真实走过的路线，**它把坡爬完了，停在坡道顶出口前那一小段**，此后没有任何推进。

### 1.2 卡点处的局部决策（`live_status.json.local_rollout`）

```
candidate_count 25     rejected: occupied 18   （其余类别全 0）
best: (-1.546, v=0.0, w=0.4)        ← 最优候选是"原地右转"
target_xy_m: (-4.675, 2.675)        ← 距机身仅 0.24 m
```

25 个 (v,ω) 候选里 **18 个被 `occupied` 一票否决**，活下来的只有 `v=0` 和 `v=0.03`。`v=0.03 m/s × 0.5 s 前瞻 = 1.5 cm`，打分里 `-2.0 × 到目标距离` 几乎不变，于是"原地转"永远是全局最优。

`T` 不是空间开口，是**坡道内侧墙在 2D 占据图上投出的"未知阴影"**：墙格长期停在 log-odds≈0.35（`README` 已记录），既不算占据也不算空闲，于是"贴墙根那一列未知格"每帧都被当成前沿。
结果就是两层判断互相打架：**全局层把墙根阴影当成"尚未探索的空间"，局部包络核对又把墙根那片占据格当成硬否决。**

### 1.4 它为什么一直重复选同一个点（`replan_history.json`，172 条）

```
167 × exploring | continuing_reachable_frontier        target = (-4.675, 2.675)
  5 × exploring | goal_not_observed_reachable_frontier_selected
最后 12 条（81.8 s → 87.3 s）的 target 逐字节相同
```

`session.py:242-254` 的滞回（"Keep a reachable exploration subgoal until it is inspected"）在 `distance > frontier_tolerance_m(0.16)` 且该格 `frontier_visits==0` 时无限续用上一个目标。**没有寿命、没有尝试计数、没有失败拉黑**，所以"永远到不了但路径永远可达"的前沿会被续用到底。

### 1.5 兜底的"卡住就拉黑"为什么一次都没触发

`session.py:738-749` 有看门狗：探索态下连续 3 s `|linear|<0.001` **且** `|angular|<0.02` 就把该前沿 `frontier_visits += 2` 并强制重规划。
但 `standstill_escape`（`session.py:705-719`）一旦判定该转身就下发 `w=±0.4`——**机器人永远在转、永远不满足"完全静止"，看门狗 30 s 一次都没触发**。这是两个安全机制互相抵消，不是参数没调好。

## 2. 论文怎么解（分四层）

### 2.1 前沿不是"点"，是"带状态的实体"

| 论文 | 机制 | 对本项目的用法 |
|---|---|---|
| Yamauchi, *A frontier-based approach for autonomous exploration*, CIRA 1997, [DOI](https://doi.org/10.1109/CIRA.1997.613851) | 前沿 = 已知空闲与未知的边界，选"到已知空闲路径代价最小"的前沿 | 基线。它假设地图干净，**不处理死胡同**，所以要往后看 |
| Zhou et al., *FUEL*, RA-L 2021, [arXiv:2010.11561](https://arxiv.org/abs/2010.11561) | 增量**前沿信息结构 FIS**：前沿以"簇"维护（中心/朝向/信息增益），被观测即更新；选点用增益-代价比 | 把逐格 `frontier_cells` 换成**簇 + 状态**；A* 只对簇中心算一次，顺带解决 A |
| Zhang et al., *FSMP*, IEEE TIM 2025, [arXiv:2502.20707](https://arxiv.org/abs/2502.20707) | 用**传感器 FOV 可见性**判定前沿（有 soundness/completeness 保证），增量 roadmap + 两阶段路径 | 直接治 §1.3 的假前沿：墙阴影里的未知格不产生前沿 |
| Zhou et al., *OTO Planner*, 2024, [arXiv:2406.07294](https://arxiv.org/abs/2406.07294) | **"只走一次"**：检测"被围合的封闭子区域"，对重复经过路径加代价；视角精化合并冗余视点 | 死胡同=封闭子区域，进去一次后整块标覆盖，而不是反复选 |
| Niu et al., *STGPlanner*（骨架拓扑）, ICRA 2025, [arXiv:2412.13664](https://arxiv.org/abs/2412.13664) · [code](https://github.com/Haochen-Niu/STGPlanner) | 增量骨架拓扑图 + 有限状态机做覆盖路径，显式抑制 **back-and-forth maneuvers (BFM)** | `continuing_reachable_frontier` 就是 BFM；骨架图天然回答"从哪个口进来、该从哪出去" |
| Batinović et al., *Shadowcasting-Based NBV Planner*, 2021, [arXiv:2109.09323](https://arxiv.org/abs/2109.09323) | 递归 shadowcasting 算增益 + **dead end resolving strategy**（死胡同内增益≈0 → 快速退出） | 唯一把"死胡同快速恢复"写进 NBV 的工作，实现最轻 |
| Cao et al., *TARE*, RSS 2021, [code](https://github.com/caochao39/tare_planner)；配套环境论文 [arXiv:2110.14573](https://arxiv.org/abs/2110.14573) | 分层：**局部规划器管"怎么走进去"、全局规划器管"下一个去哪"**，两者共用同一张前沿图；local 层负责把可达区域啃干净 | 与你现在的"前沿 + A* + rollout"结构最像，**改造量最小** |

> 共性三条：① 前沿必须有**生命周期**（发现→选中→到达→失效/拉黑）；② 前沿判定必须**考虑遮挡**；③ 选点用**路径代价**，不是欧氏距离、更不是加罚后的格步数。

### 2.5 四足为什么不能直接套轮式 DWA

1. DWA 的速度空间是 (v, ω)，四足**全向**，恰好禁掉"横移一步"这条最有效的脱困动作；
2. 2D 足迹 + 固定高度膨胀把可跨碎石/台阶判成 lethal，窄口在代价地图上"被关死"；
3. 腿摆/机身起伏使实际速度≠指令速度，progress checker 更易误触发；
4. 低速微调受步态/落脚约束，必须步态层配合（步频、抬腿高度）。

- 高程图：Miki et al., IROS 2022, [DOI](https://doi.org/10.1109/IROS47612.2022.9981507)
- 可踏性进规划：Grandia et al., IEEE T-RO 2023, [arXiv:2208.08373](https://arxiv.org/abs/2208.08373)（`总体技术方案.md` 已收录）
- 四足"被冻住"的实测现象与 **holonomic recovery**：Sathyamoorthy et al., *VERN*, 2023, [arXiv:2303.14502](https://arxiv.org/abs/2303.14502)（用 freezing rate 作指标，横移脱困）
- 你的 `总体技术方案.md` §118 原话："局部规划优先验证已安装 TEB，**按实际横移、后退和转向能力配置**"——本文 §4.6 就是这条的落地。

## 3. 全局路径与局部执行的耦合（决定"会不会停在路径上"）

- **沿路径进度项**：MPCC 把"进度"与"横向误差"分开建模，避免只罚横向误差时"停在路径上"就是最优解。Lam, Manzie, Good, CDC 2010, [DOI](https://doi.org/10.1109/CDC.2010.5717042)
- **同伦类重选**：TEB 的 homotopy class planning（§2.3）
- **可见性图动态断边**：FAR, Yang et al., IROS 2022, [arXiv:2110.09460](https://arxiv.org/abs/2110.09460)
- **工业现成实现**：Nav2 Route Server（预定义导航图 + `ReroutingService`）才是"拓扑路线 + 自由空间局部执行"的成品
- 有文献把"path tracking with progress guarantee"当标准命名——**未核实，不引用**；等价机制是 MPCC 进度项 + 进度看门狗。

## 4. 落地：按性价比排序的 6 处改动

> 不动分层结构，只补"状态"和"判据"。前 3 项对应 `README` 里"留待下一轮：贴墙硬约束 + 真正的路径跟随"。

### 4.1 给前沿续用加寿命与失败计数（10 行，最高优先）

`session.py:242-254` 的续用分支加状态机：

```python
st = self.frontier_state.setdefault(prev_target, {"t0": now, "replans": 0, "last_progress": now})
st["replans"] += 1
if (now - st["t0"] > 15.0                      # 单片前沿寿命
        or st["replans"] > 30                  # 续用次数
        or now - st["last_progress"] > 5.0):   # 无位移秒数
    self._blacklist_frontier(prev_target, radius=0.45)   # visits += 大权重
    self.last_replan = -math.inf
else:
    self.plan = continuation
```

**15 s / 30 次 / 5 s** 取自：本机 `sensor_lab` 探索复跑"751.9 s、35 个前沿"的量级，以及 Nav2 `SimpleProgressChecker` 的 0.5 m / 10 s 同数量级。对应论文：FUEL 的 FIS 状态、OTO 的封闭子区域代价、TARE 的 local/global 协调。

### 4.2 让卡死看门狗与逃逸层不互斥（改 1 个条件，最高优先）

`session.py:738` 把 `abs(angular) < 0.02` 换成**净位移速率**：

```python
moved = math.hypot(pose[0] - self.blocked_pose[0], pose[1] - self.blocked_pose[1])
if moved < 0.02 and now - self.blocked_frontier_since > 3.0:
    self._blacklist_frontier(self.plan.target_xy, radius=0.35)
    self.lock_escape_direction(now)   # 见 4.4：锁定单向旋转，别左右来回
```

与 DWA deadlock 判据、Nav2 progress checker（位移而非零速）一致，顺手修掉 §1.5 的双机制抵消。

### 4.3 前沿检测加遮挡 + 净空过滤（高优先）

`planner.py:119-139` 生成 `frontier_cells` 时两条廉价过滤（不必上全量 shadowcasting）：

1. **前沿格本身必须是 `known_free & ~blocked`**（现在只保证"路径可达"，前沿格可能在未知带里，A* 到了、局部进不去）；
2. **`grid.clearance(frontier) ≥ body_corner_radius(0.372 m)`**，否则它是墙根阴影而不是开口。

这就是 FSMP 的 FOV 判定 + Batinović shadowcasting 的轻量版，纯几何、无新依赖（`grid.clearance()` 已有）。

### 4.4 局部采样改成"一致积分原语" + 单向逃逸（高优先）

`session.py:565-572` 现在是 `velocities × turns` 笛卡尔积。改为少量原语（每类做 0.5 s 一致积分，与 DWA 同构、开销更小）：

```
弧形前进  (0.15,±0.4) (0.15,±0.2) (0.08,±0.4) (0.08,0)
爬行      (0.03,±0.2) (0.03,0)
原地      (0,±0.4) (0,±0.2)
倒车      (-0.08,0) (-0.08,±0.2)          ← recovery 已有，但没进常规 rollout
```

`session.py:686` 打分加两项：**沿路径弧长进度正奖励**（`+0.5·Δs`，MPCC 思路）+ **离开卡死点的逃逸项**（距最近卡死点 >0.3 m 才给分，Bug2 脱离判据）。并在逃逸期内**锁定单向旋转方向**（对当前的 ±0.4 交替是致命的多余自由度）。

### 4.5 前沿格与"已探索"语义打通（中优先）

`_mark_frontier_visited` 只在 `frontier_reached`（距离 ≤0.16）时调用。应改为：**任何"选中但 N 次未抵达"的前沿同样进入访问计数**，并让 `planner.py:130` 的惩罚量级追上（现在 `+3.0×min(visits,3)` 相对 `preferred_blocked` 的 +2.0/步过小）。

### 4.6 把横移（vy）纳入局部原语（中优先，需接口扩展）

本案目标就在机身右侧 0.24 m；**全向四足一步横移即可解除死锁**，而现在的 `(v, ω)` 空间结构上排除了这个解。这正好是 `总体技术方案.md` "按实际横移、后退和转向能力配置"那条的落地，也与 §2.5 的四足文献一致。
代价：`VelocityCommand` / `ros1_twist` 适配器 / mocap 执行器要加 `vy`，且需实机确认横移步态可用——**列为 P1，不阻塞 4.1–4.5**。

### 4.7 顺手修（2 行）

`session.py:722` 的 `"valid_count": 0 if best is None else 1` 恒为 1，应改为 `len(samples)`。这轮实际 8/25 有效，但日志读不出来——正是排查时最误导人的地方。
