 1. 先了解赛事边界

 本赛题使用固定版本的 Unitree Go2 和 MuJoCo 环境。参赛团队使用公开资源训练策略，通过 Robotics

 Bench 提交作品；赛方在统一环境中完成兼容检查、验证或评测。

 请注意：

• 资源、机器人、传感器和模型接口均以版本及 SHA-256 绑定；

• 公开训练场景用于开发和接口验证，不等同于正式隐藏场景；

• 任务可见不代表远程执行资源当前可用；

• “执行成功”只表示工作流运行结束，“质量通过”才表示达到当前任务的质量门槛；

• 参考任务的质量门槛不等于赛事积分或排名规则；

• 当前没有已验收的完整路线或足球检测合格基线，示例运行成功不代表能够完赛或得分；

• 当前参考能力不包含未知地图探索、动态避障或任意类别检测。

 参赛者不需要直接调用评测接口或填写运行配置标识。所有参赛操作均从 Robotics Bench 当前赛事页面完

 成。

 2. 标准参赛流程

 报名通过 → 阅读赛事页面和本指南 → 下载并校验资源 → 配置固定环境 → 本地训练与验证 → 导出 ONNX

 → 按赛事页面要求整理作品 → 队长上传一个作品版本 → 选择参评版本 → 查看执行和结果。


  阶段              完成标准


  资料准备            文件版本和 SHA-256 与赛事页面一致


  本地验证            场景可加载，观测、动作、重置和推理接口一致


  模型导出                ONNX 可被规定版本的 ONNX Runtime 加载，批次维满足接口要求


  平台提交            队长上传成功，并在作品历史中选择正确参评版本


  执行判读            区分执行状态、质量状态和赛事成绩


 3. 公开训练资源

 3.1 从哪里获取

 只从 Robotics Bench 当前赛事的“赛事资料”下载。平台发布的 ZIP 文件名、版本、SHA-256、

 MANIFEST.json 和 SHA256SUMS 共同标识正式资源。本文不固定写入某个尚未发布的本地草案版本或哈希。

 下载后校验：

•  ZIP：按赛事页面或同目录 .sha256 文件核对；

•  macOS：在展开目录运行 shasum -a 256 -c SHA256SUMS；

•  Linux：运行 sha256sum -c SHA256SUMS；

•  Windows：使用 Get-FileHash -Algorithm SHA256 并与 SHA256SUMS 比对。

 5. Go2 Agent 模型接口

 5.1 完整 Agent

 完整场景控制接口为 go2-agent-v1：


  张量                   dtype                  含义


   obs                        float32                                      [B,189] 结构化观测


   rgb                        float32                                       [B,3,64,64] RGB 图像


   state                      float32                                       [B,32] 显式记忆状态


   sensor_meta              float32                                         [B,8] 传感器帧龄与有效性信息


   actions                    float32                                       [B,12] 关节动作，范围 [-1,1]


   next_state                 float32                                       [B,32] 下一步记忆状态

 模型批次维必须是动态维。每回合开始时 state 清零；即使提交声明不启用记忆，模型仍须接受 32 维 state

 并输出 32 维 next_state。

 189 维 obs 按以下顺序组成：


  内容           维数                   处理


  机体角速度              3                    乘 0.25


  投影重力                3                    机体坐标系


  公开速度指令            3                    前进、侧向、转向


  关节位置相对默认姿态     12                   固定关节顺序


  关节速度                12                   乘 0.05


  上一步裁剪后动作         12                   固定关节顺序


  每个水平角最近 LiDAR 距
                          72                   按任务规范归一化
  离


  每个水平角 LiDAR 有效标
                          72                                   0 或 1
  志


  合计                    189                   不能调换顺序

 5.2 RGB 与目标检测

 场景相机基线为 320×240、10 Hz、垂直视场 60°，不含深度。送入模型前使用像素中心双线性缩放到

 64×64，转为 CHW float32 并除以 255；不使用任意裁剪或训练时自定义预处理替代正式预处理。

 目标检测接口为 go2-detection-v1：

•  输入：obs，[B,3,64,64] RGB 图像；

•  输出：[B,5]；

•  输出顺序：confidence, xmin, ymin, xmax, ymax；

• 坐标与置信度范围均为 [0,1]；

• 任务只检测任务包指定的单一类别。

 完整 Agent 任务要求的模型角色由赛事页面发布的任务规范决定。当前公开组合任务包含控制与足球检测两

 个角色；如赛事采用该组合任务，两个角色都必须满足对应的模型接口。不要用“缺少检测模型时按零分处

 理”代替完整性校验。

 5.3 LiDAR

 公开 Agent 任务的 LiDAR 基线为：

•   72 个水平角 × 9 个垂直角；

• 水平视场 360°，垂直视场 96°；

• 距离范围 0.05–12 m；

•   10 Hz；

• 排除机器人自身碰撞体；

•   189 维观测仅保留每个水平角在规定机体高度带内的最近有效回波和有效标志。

 无效回波不能当作“无障碍”。传感器位置、方向、高度带、噪声和丢失率以任务包 sensors.json 及其

 SHA-256 为准。

 6. 训练、验证与导出

 6.1 建议训练顺序

1 先加载 Go2 和单项障碍，验证重置、站立和动作方向。

2 检查 12 个关节的名称、顺序、默认姿态和限幅。

3 对照第 5 节构造观测，记录每段维数和归一化。

4 先完成短回合与单项障碍，再进入完整公开场景。

5 单独检查 RGB 预处理、检测输出范围和空目标画面。

6 使用多个本地种子验证，不以单段成功视频代替统计结果。

7 导出 ONNX 后，使用 CPU ONNX Runtime 重新加载并做数值对比。

 6.2 ONNX 导出检查

• 文件扩展名为 .onnx；

•  输入输出名称、dtype、维数和动态批次与第 5 节一致；

• 模型不依赖网络、外部动态库、容器或任意本地路径；

 7. 作品提交

 7.1 当前平台操作

 只有队长可以提交：

1 在赛事页面打开作品上传入口；

2 按页面当前要求选择一个文件；

3 上传后等待文件状态就绪；

4 在作品历史中选择要参评的版本；

5  核对文件名、大小、SHA-256、选择状态和截止时间。

 当前平台存储层允许的单文件类型包括 PDF、ZIP、MP4、PNG 和 JPEG，单文件上限为 100 MiB；这是平台

 通用上传边界，不等于本赛题允许用任意格式提交模型。本赛题最终要求的作品格式、ONNX 数量和 ZIP 目

 录结构，以当前赛事页面发布的提交说明为准。 页面未发布专用结构前，不要自行把 Go2 服务 API 示例当

 作参赛提交格式。

 平台不会因上传新版本而自动替换已选参评版本。队伍应在截止前主动核对选择状态。不要绕过赛事页面直

 接调用评测接口或自行构造运行配置。

 7.2 提交前自检

 □  使用赛事页面发布的正确资源版本

 □   MuJoCo、Python 和 ONNX Runtime 版本一致

 □   ONNX 输入输出名称、动态批次和 dtype 正确

 □  模型 SHA-256 已保存

 □  不含密码、令牌、个人敏感信息或联网依赖

 □  队长上传的是预期文件

 □  已选择正确参评版本

 □  已记录截止时间和页面状态

  状态              解释


  succeeded          技术执行完成，继续查看质量状态


   failed / timed_out       执行失败或超时，查看失败阶段和已保存产物


   quality passed         达到当前任务包的质量门槛


   quality failed          执行完成但没有达到质量门槛


   skipped            前置质量门未通过或流程规则跳过该步骤

 正式评测与参考验证应分开理解：

• 公开任务用于兼容性和开发验证；

• 正式任务可使用冻结的不同布局、路线、目标配置和种子；

• 正式任务不会向模型提供裁判真值；

• 队伍只能查看自己按赛事规则开放的产物；

• 排队等待和服务器墙钟时间不直接作为仿真内得分依据。

 服务可产生指标、逐回合事件、轨迹、视频和质量结论，但不会仅凭服务结果自动形成赛事名次。正式计分

 权重、违规后果、同分规则、结果公示与异议期限均以当前赛事页面发布的正式规则为准。

 9. 公平竞赛与禁止事项

 禁止：

• 获取、推断、传播或利用正式隐藏布局、裁判真值或未公开验证资料；

• 绕过鉴权、截止时间、参评选择、模型接口或资源限制；

• 在模型中加入联网下载、远程控制、外部程序或动态代码执行；

• 使用未申报、无权使用或许可不兼容的模型、数据和资源；

•  伪造模型来源、SHA-256、日志、视频或结果；

• 攻击平台、其他队伍或共享执行资源。

 发现安全问题时停止复现，不公开漏洞细节，按赛事页面的安全报告渠道提交。

 10. 异常与异议材料

 遇到异常时保存：

• 赛事和队伍名称；

• 作品文件名与 SHA-256；

• 任务或工作流标识；

• 发生时间和页面状态；

• 错误信息与最小复现步骤；

• 不含密钥和个人敏感信息的必要截图或日志。

 账号、报名和作品状态问题由队长或老师按赛事正式通知联系组织方；执行、接口和计分问题按赛事页面公

 布的技术支持或异议入口提交。只有正式通知列出的渠道和时限有效。
